# Codex 작업 지시서 — MAWD Relay P0

## 목표
백엔드 저장소 `Olcho/BabmuwonBE`에 **실행 가능하고 자동 테스트 가능한 로컬 Relay**를 구현한다. 프론트엔드 저장소 `Olcho/BabmuwonFE`는 별도 담당이므로 코드를 수정하지 않는다.

## 기준 및 범위
기준: 기능명세서 v0.3 최종본 (2026-11-14), 특히 **7장 F5, 8장 Relay, 9장 테스트, 10장 구현 순서**.
제품 기능: 학교가 작성한 확정 엑셀 식단 → 로컬 규칙 기반 알레르기 관리 → S1~S5 문서 생성/승인 → S2를 카카오 알림톡으로 안내. 백엔드는 이 가운데 외부 API 중계와 발송 통제를 담당한다.
**Vapi, Readray, 로컬 LLM, SMS/LMS, 보호자 답장, 자체 학생 건강정보 DB는 제외.**

## 단계 0: 기존 상태 조사
- 현재 리포지토리의 파일 및 브랜치를 확인한다.
- 사용자가 이전에 제공한 `MAWD_backend_Relay_v0.1.zip` 또는 추출된 `mawd-relay-backend/`가 Codex 작업 환경에 제공되어 있다면 먼저 분석하고 검증한다.
- 파일이 없다면 출발 소스가 없음을 명시하고 새 프로젝트를 생성한다. ZIP이 존재한다고 가정해 임의 경로를 만들지 않는다.
- 일반 `main` 직접 작업 금지. `codex/relay-foundation` 브랜치를 생성한다.

## 단계 1: 최소 실행 구조
- Node.js 22+ 및 TypeScript로 구현한다. 로컬 실행은 `127.0.0.1:3000`.
- 필요한 경우 Node.js 내장 HTTP 서버로 충분하다. Express/Fastify 전환은 팀과 합의하기 전 강제하지 않는다.
- `npm run build`, `npm test`, `npm start`가 재현 가능해야 한다.
- `.env.example`, `.gitignore`, README, 프론트엔드 API 문서 제공.
- `GET /health` 제공. 환경변수/토큰/요청 본문 노출 금지.
- CORS 출처 제한 + 실제 인증 처리. CORS만으로 API 호출 권한이 제어된다고 간주하지 않는다.
- Mock 기본값. 비밀정보 없이 시작 가능. 실제 발송은 명시적인 별도 설정이 있어야만 허용.

## 단계 2: v0.3의 5개 API
| Endpoint | 입력 | 연동 | 검증 |
|---|---|---|---|
| `POST /ai/s2-news` | `month`, `menus[]` | Liner Router | 검증된 월, 공개 메뉴명만 |
| `POST /ai/nutrition` | `topicId` | Liner Search Agent | 사전 정의된 주제 목록 |
| `POST /ai/substitute-evidence` | `allergenNo`, `foodName` | Liner Search Agent | 번호 1~19, 후보 메뉴명 |
| `POST /ai/s5-body` | `counts` | Liner Router | 집계 최소화, 3명 미만 병합값, 재식별 위험 검토 |
| `POST /send/alimtalk` | `batchKey`, `month`, `recipients[{memberId,phone}]` | Channel Talk | 발송 승인, 검증, 중복 방지 |

- 4개 AI API에는 자유 프롬프트 입력 불가. 서버에서 정해진 템플릿으로 프롬프트를 조립.
- 요청 JSON 필드 허용목록과 최대 크기 제한. 잘못된 필드는 400.
- Liner 요청/응답 규격은 현재 공식 문서 대조 후 구현. Search Agent의 스트리밍/SSE 여부 및 실제 에러 이벤트 처리 검증. 공식 문서 확인 전 응답 스키마 추정하지 않는다.
- 에러/타임아웃/429 처리 및 모의 응답과 실제 응답 구분. 캐시 및 Liner 호출 속도 제한.
- AI 결과는 `reviewRequired: true` 등 문서 담당자가 승인해야 한다는 상태를 포함.

## 단계 3: Channel Talk F5
- 카카오 비즈니스 채널, 채널톡 계정, 승인된 알림톡 템플릿과 캠페인 이벤트 연동은 **외부 사전 조건**이다.
- 채널톡 사용자 upsert와 이벤트 생성 API의 **최신 공식 문서**를 확인하여 구현. `/open/v5` vs `/open` 경로와 사용자 ID 형태를 실계정에서 검증한다.
- `lunch_notice_requested` 이벤트가 실제 알림톡으로 이어지는지는 **미검증**임을 명시.
- AI가 생성한 자유 텍스트를 알림톡 템플릿에 직접 넣지 않는다. 승인된 고정 템플릿의 `month` 변수만 사용.
- S4 개별 알레르기 안내문 및 학생별 정보는 알림톡에 넣지 않는다.
- `batchKey`로 중복 발송 차단. 같은 배치 중복 요청 409; 다중 요청 경쟁 조건에도 안전해야 함.
- 이벤트 전송 요청 성공은 delivery success가 아니다. 기본 `unknown`; 실제 증거 없으면 수신 성공 표시 금지.
- 전송 결과 불명확한 요청에 대해 자동 재시도 금지. 실패한 요청만 조건부 재시도.
- **주의:** 프론트엔드 IndexedDB 승인 플래그는 클라이언트가 변조할 수 있다. 실제 서버 측 문서 승인 검증이 없다면 인터넷 공개를 막고 로컬 데모로 제한한다.
- 로컬 파일 저장소는 클라우드 배포 시 영속성을 보장하지 않는다. Render 배포 설정을 임의로 추가하지 않는다.
- 채널톡 도착 여부 조회/웹훅 기능은 지원 확인 전 미구현/미검증 표시.

## 단계 4: 안전성 검증 및 테스트
- 학생 이름/가명/학교명/학년반번호/전화번호 포함 데이터의 Liner 전송 차단 테스트 최소 20종.
- 인가 없는 요청 401/403; 잘못된 스키마 400; 중복 배치 409; 업스트림 실패 시 안전한 오류만 반환.
- 비밀정보가 응답/로그/백업에 섞이지 않는지 검증.
- 라우트별 Mock 테스트, 특히 `simulated`과 `deliveryStatus: unknown` 구별.
- 같은 `batchKey` 동시 발송 요청 경쟁 테스트 및 서버 재시작 후 중복 방지 테스트.
- 발송 상태를 재시도할 때 upsert 실패/이벤트 전송 불확실을 명확히 구분.
- 실서비스 개인정보 보호 완성 또는 실제 알림톡 발송 성공을 증거 없이 선언하지 않는다.

## 프론트엔드 협업 계약
`docs/FRONTEND_API.md`를 만들어 요청/응답 JSON, 상태 코드, 인증 헤더, CORS Origin, localhost 실행법, Mock 상태 설명을 명시한다. 문서로 계약을 전달하되 FE 저장소에는 변경하지 않는다.

1. 현재 저장소 진단 및 초기 구조

4. 알림톡 mock, 중복 및 상태
